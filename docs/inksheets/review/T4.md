# T4 — Remote, controllers, Play together (tester findings)

Tester T4, 2026-10-08/09. Worktree `C:\PDF Draw App\.claude\worktrees\agent-a77db4868a4ca5732`.
Tests: `sheets-desktop/src/test/kotlin/com/inksheets/desktop/review/T4*.kt` (results log: `sheets-desktop/build/t4/results.txt`).
All on loopback / one JVM. Bluetooth, USB, real MIDI, real Wi-Fi/eduroam were NOT available (simulated: sockets, a swallowing relay, a fake ControllerInput).

Solid after a real try: wire latency (press -> command and -> tick < 1 ms on loopback; with 50 followers a page turn reaches all in 1 ms, a note in 3 ms, 50 join in 35 ms), reconnect after host/leader restart (1.3-2 s, no tap), follower restart resumes (not after 4 h), follow modes and rapid turns end on the right page, instrument-filtered notes, joins go to the log not the screen, odd join links parse sanely, sweeps map 0/64/127 to 40/141/240 bpm.

## Round 1-2: as intended / combinations

**T4-01 · S2 · Leader's follower count merges followers with the same device name.** 12 devices all named "Tablet" -> strip says "Leading · 1"; 15 "Pixel 7" + 5 "SM-X516B" -> count 2; one leaving logs nothing. Name is the only identity (`followerCount = followers.map{name}.distinct()`, `lastSeen[name]`); Android default name is `Build.MODEL`, so a 50-person band on one phone model is normal. Fix: count connections / give each follower an id in Hello. Evidence: `T4CompanionCoreTest`, `T4PlayTogetherTest.twelve whole devices`. Status: fixed 7093f2f (each follower sends a per-device id in its hello; the leader counts and de-duplicates by it, by name only for older versions).

**T4-02 · S2 · Two leader messages within one second: the second is lost.** Follower dedups by `"n"+at/1000` (`Companion.heard`). STOP then "Look up" together -> noticeCount=1. Fix: dedup on full ms + text. Evidence: `T4PlayTogetherTest.two notes in the same second`. Status: fixed 7093f2f (a note carries a unique id; followers de-duplicate on it, older leaders and Bluetooth by second + words).

**T4-03 · S2 · A message sent while the follower is on Home is kept and then covers the next song.** Only `NotePopup` (mounted over a song) times it out; `noticeShowing` still true 16 s later on Home. Old "STOP" covers the next song for 15 s; on Home the player never sees it. Show on Home too and expire by age. Evidence: `T4PlayTogetherTest.a note sent while...`. Status: fixed 7093f2f (a note nobody saw within its window - arrived on Home - is dropped, not shown over the next song).

**T4-04 · S3 · Urgent cover replaced by a plain note; and it is not "until tapped away".** STOP then "Next up" 1.1 s later: the cover vanishes untapped (no queue). UI says "until each player taps it away" but `NotePopup` removes it after 15 s. Status: fixed 7093f2f (an urgent cover stays until tapped; later messages wait behind it and show after).

**T4-05 · S3 · A follower that never answers heartbeats is counted forever** (tablet in a bag; read timeout is armed only after the first Pong). A socket that never says hello counts as one follower named by IP. Evidence: `one follower that stops reading`, `NO HELLO`. Status: won't fix (a stale-follower sweep needs a protocol change on the follower side and Wi-Fi tests on device; counted by connection now, so it no longer hides).

**T4-06 · S3 · "Show me" has four radios, one 70 characters long** ("Automatically - the same page when it's the same part, otherwise my own part"): too much for 50 non-technical players. Default AUTO is right; hide the rest behind "More". "Go to the leader" itself works (reopens the part from Home). Status: won't fix (product decision: which follow modes to hide behind More).

**T4-07 · S3 · Raw action names leak into the remote's status line**: preset tiles, typed messages, Set/Songs/Parts pickers send `name = action`, so it reads "preset ✓", "set-entry ✓", "parts...". The Tap button gives no feedback on its first tap. `RemotePanel.kt:990,1071,1074`. Status: fixed 7093f2f (presses are named in words: the message text, the song, "Next page").

**T4-08 · S2 · "✓" is receipt, not effect.** A message button to a device that is not leading gets a tick and does nothing; AUDIO_* with no recording, LISTEN when off, likewise. A gig user reads ✓ as done. Host should answer "did nothing: not leading". Status: fixed 7093f2f (the device answers a second "got" with a reason - not leading, no recording playing, Listen off, no song open - and the remote shows it instead of a tick).

**T4-09 · S3 · Finding songs on the remote.** "All songs" (set page) has A-Z letter jumps but no Find; the "Songs..." picker has Find only above 8 items, plain `contains` (no accent/word matching like Home's `matches()`), in a 460 dp box. See "useful" below. Status: fixed 7093f2f (Find on the set page for setlists/songs/set, and the pickers use the app's matches()).

**T4-10 · S3 · Nearby lists hide devices with the same name as this one** (remote and Play together): two identical phones never see each other. Status: fixed 7093f2f (a device is hidden only if it is this device's own address, not by name).

## Round 3-4: not as intended / break it

**T4-11 · S1 (robustness on shared Wi-Fi) · The remote host reads an unbounded line before any key check.** 96 MB one-line, no hello: accepted, heap +300 MB, dropped after 10 s. Hosting persists (`K_HOSTING`) and binds 0.0.0.0 each start; anyone on the network can OOM the app mid-gig. 400 idle sockets = 800 threads, no cap (a real remote still connected, 1.4 s). Cap line length and unauthenticated connections. Evidence: `T4RemoteCoreTest`. Status: fixed 7093f2f (lines bounded before and after the key, at most 16 connections without the key with the oldest let go first, key within 5 s).

**T4-12 · S3 · Key has no rate limit**: 1635 wrong keys in 3 s, no delay/lockout. Status: won't fix (the key is only 6 characters on a LAN; a lockout would let an attacker lock the real remote out - needs a product decision).

**T4-13 · S3 · A dead link takes 8 s to notice, ~10 s to be usable.** Relay black hole: 5 presses return seq 1-5 with no error, host got 0; client flagged lost at 8.0 s (limit 7), reconnected 10 s after cut. UI marks the press "not received - Reconnecting" after 2.5 s (good) but header still says "Controlling X" until then. Add a "no signal" bar after 3 s without a ping (host pings every 2 s). Status: fixed 7093f2f (header says "No signal ... trying again" after 3.5 s without a heartbeat).

**T4-14 · S2 · Desktop page-turn pedals have no auto-repeat guard.** Android `PedalKeys` acts only on `repeatCount == 0`; Windows `Main.kt onKeyEvent` runs `Perform.run` on every KeyDown and Compose delivers OS auto-repeat as KeyDown: a keyboard-type pedal held >0.5 s races through pages. By code reading (no OS auto-repeat in a test). Status: fixed 7093f2f (desktop ignores a repeated key-down for bound page actions, as Android does).

**T4-15 · S2 · Sequences have no re-entrancy guard.** Pedal bound to a 3-step sequence pressed twice 250 ms apart ran 6 steps interleaved at ms [5, 305, 324, 605, 624, 924]; same in the remote deck (new coroutine per press). Evidence: `T4ControllerTest.a pedal pressed twice quickly`. Status: fixed 7093f2f (a second press while a sequence runs is ignored, on the remote deck and on a controller).

**T4-16 · S3 · A fader that does nothing says nothing**: volume/speed sweep with no recording playing: no message. Status: won't fix (a fader sweep has no per-move answer; it would need the host to say 'nothing playing' once per sweep - product decision).

**T4-17 · S3 · Learn / place modes swallow every control, no timeout, no DisposableEffect.** While `learning`/`placing` is set bound page-turn pedals are consumed; cancel happens only in the dialogs' own dismiss. Any other exit leaves pedals dead until restart. Evidence: `T4ControllerTest.learning swallows`. Status: fixed 7093f2f (learning/placing ends by itself after 60 s the next time anything is heard).

**T4-18 · S3 · Bindings need the exact device name.** Windows Java Sound names change with the USB port; "any device" (`device=""`) is in the model but not offered. Two identical pedals collapse into one entry (`DesktopMidiInput` keyed by name). Simulated; real names unchecked. Status: fixed 7093f2f in part (a binding matches the same device under another USB port prefix/suffix); an "any device" choice and telling two identical pedals apart still need UI/product work.

**T4-19 · S4 · Android (read only):** POD Go unplug joins the worker up to 1.5 s on the main thread and an immediate replug is ignored (`if (running != null) return`); `AndroidRemoteBluetooth.ready()` may fire the "turn on Bluetooth" intent at every start while hosting persists. Unverified on device. Status: won't fix (Android only, unverified on device; not compiled here).

**T4-20 · S3 · Remote vertical swipes vs a scrolling button grid.** `RemotePager` treats any vertical swipe >64 dp on Buttons as a page change; on a phone on its side cells fall below 56 dp so the grid scrolls — scrolling can switch to Tuner/Reading. DRIVEN (`T4RemoteScreensTest`, phone 844x390): the fourth row (Bookmark/Metronome/Count in is row 3, Toolbar / All tools / Play row is cut at the bottom) cannot be reached: an upward swipe over the grid jumped to the Reading page. Landscape shot `sheets-desktop/build/t4/shots/landscape-buttons.png`: the REC/SET edge tabs also sit over the first/last button column. Upright 390x844 fits the default 12 buttons. Status: fixed 7093f2f (when the button grid scrolls, a vertical swipe over it scrolls and never changes page). The REC/SET edge tabs sitting over the first/last button column are not changed.

**T4-21 · S2 · A momentary pedal held >3 s while learning is stored as "every press", so its release turns a second page.** Learned with a 200 ms press: everyMessage=false (correct). Held 3.3 s before release: everyMessage=true; then each press+release turned 2 pages. The learn dialog only says "once, and let go" and offers no switch to correct it besides the POD-Go-only chips. `ControllerHub.learnFrom` (3000 ms window). Evidence: `T4ControllerTest.learn a switch...`. Status: fixed 7093f2f (the let-go window is 15 s, and a binding row can be tapped to change when it counts: when pressed / every message / when let go).

**T4-22 · S3 · Replugged pedal on another USB port fires nothing** (binding to exact name; simulated "2- T4 Pedal" -> 0 actions). Confirms T4-18. Status: fixed 7093f2f (same as T4-18). Controllers off/on works with no restart (1 action after re-enable).

Controller toggle modes (driven through the fake input): POD-style 127,0,127,0 -> every press 4, when it lights 2, when it goes dark 2 (correct); 100,5,100,5 same; a latching switch sending only 127: "lights" fires every press, "dark" never (correct but invisible: show last value on the binding row); note on/off -> 1 per press; program change with a default binding is one-way (2 of 3) as documented. The binding row in Settings shows only "every press" or nothing: "when it lights / when it goes dark" appears only in the POD Go dialog, so generic MIDI users cannot see or change the mode (S3, `ControllerSettings.BindingRow`).

## What would make it genuinely useful
- **Find on the remote's main page** (type "fi" -> Fight Song, tap = go), **Recent songs**, and **next 3 of the set** always visible; the set grid remembers its place.
- "No signal" bar on the remote after 3 s of silence; host answers "did nothing: not leading / nothing playing".
- Leader check: **"N of M on this page"** (by connection, not name), tap to see who is not.
- Messages: urgent covers that must be acknowledged, a queue (STOP, then Look up), re-send to those who have not tapped.
- Controllers: "Test my pedal" list of the last 12 events and what each would do (hub already keeps `recent`), and an Any-device binding so replugging works.

**T4-23 · S2 (found while re-running T4ControllerTest) · `ControlEvent.fromMidiBytes` could loop forever on stray bytes.** A system byte (0xF1-0xF7) was kept as the running status, so a data byte after it never advanced the read position: `T4ControllerTest.midi bytes` hung for 20+ minutes on the 5000 junk bytes. Status: fixed 7093f2f (running status is kept only for channel messages; `T4FixesTest.stray system bytes...`).
